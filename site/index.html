Inside

Route like Remix. Own the terminal.

A stack router, a view lifecycle, and a layout engine on your machine. One framework, three primitives that compose.

Route Router · Shells · Modals

Push, pop, and replace over a route table. Persistent chrome survives navigation; modals render over the previous route with a backdrop and locked focus.

// routes are just constructors router.route("/", Dashboard::default()); router.route("/settings", SettingsForm::default()); // from any view: cx.navigate("/settings"); cx.back();

Render taffy · cells · 60 FPS

Declare flex containers; taffy computes continuous layout and the quantization engine snaps it to cells — no overlaps, no drift, no zero-width collapses.

pub fn quantize_rect(layout: &Layout, parent: Rect) -> Rect

Restore Guard · Panics · Signals

Every panic, SIGINT, and SIGTERM restores raw mode, the alt screen, and mouse capture before exit. Logs go to a file, never the live screen.

// installed once, before user code runs install_panic_hook(); install_signal_handlers(&handle);

Architecture

Your app. Your runtime. Your frame budget.

Three isolated tiers. Heavy async work or a resize never causes a frame drop or input lag.

  1. 01
    Ingestion thread

    A dedicated OS thread polls input and forwards typed events over a bounded channel.

  2. 02
    Tokio pool

    Loaders, network, filesystem, and cx.spawn tasks. Results return only as typed actions.

  3. 03
    UI thread

    Synchronous drain — input, then actions, then ticks — then a pure render and a ≤60 FPS flush.

  4. 04
    Terminal guard

    RAII raw mode, alt screen, and mouse capture, with panic and signal hooks that always restore.

What you end up with

VeloceApp wires the tiers together. Views stay pure state machines: update(action, cx), no locks, no lifetimes in user code.

VeloceApp::new() .route("/", Dashboard::default()) .run().await

Get started

Three steps from install to first frame.

  1. 01
    Step 1: Depend

    Add veloce = "0.1" to Cargo.toml. Stable Rust, no nightly features.

  2. 02
    Step 2: Declare

    Implement View for one struct — load, update, view — with flexbox children.

  3. 03
    Step 3: Run

    VeloceApp::new().route("/", view).run().await. Press q to quit; the terminal is restored.

Engineering

Built in the open. Proven, not asserted.

A row is WORKS only when an automated test that drives the real code passes — including real PTYs for panic and signal safety. Reading code is never proof.

Panic safety

Panics inside view() and update() restore the terminal on a real PTY, every run.

Layout invariants

No overlaps, no zero-width collapse, no drift at depth 12, fuzzed 1×1…500×200.

Concurrency

10,000 interleaved events with zero deadlocks; key echo unaffected at 1,000 actions/sec.

Hydration

Fallback on the first frame, no flicker after load, mid-load navigation cancels the task.

Routing

Primitives

FAQ

Questions people ask before writing an event loop.

Do I write my own event loop?

No. VeloceApp::run owns the ingestion thread, the Tokio runtime, the priority drain, and the 60 FPS flush. You implement View and declare routes.

How do background tasks update the UI?

Through cx.dispatcher() — a cloneable typed sink. Move it into any future; dispatched actions land in update() on the UI thread. No locks, no channels in user code.

How does flexbox work on a cell grid?

taffy computes continuous layout; quantize_rect rounds absolute edges once, clamps every child inside its parent, and forces a 1-cell minimum when taffy assigned a positive size. Text participates via a measure function, so wrapping is layout-aware.

What happens when my view panics?

A panic hook restores raw mode, leaves the alt screen, and disables mouse capture before the default hook prints the backtrace. Proven on a real PTY for panics inside both view() and update().

Does it work on macOS and Windows?

Linux x86_64 is verified here (build + PTY e2e). macOS and Windows (WSL/Windows Terminal) are owner-verify — the code paths are portable crossterm/ratatui, but we have no cross toolchain in this environment.

Is it on crates.io?

Not yet — publishing needs the owner's token and is tracked as an owner-verify step. File manifests are package-validated; releases will go leaf-crate first.

What is intentionally out of scope?

Hot-reload/dev-server, mouse-wheel scrolling, non-terminal backends, and a memoized layout cache. The full deferred list lives in the parity doc.

Where are the docs?

On the Blume docs site — design note, checklist with proofs, progress log, decisions, and parity — all rendered from the repo's own markdown.
